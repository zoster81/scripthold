# Scripthold Development Roadmap

This file tracks **current and future work only**. Completed changes belong in [`CHANGELOG.md`](../CHANGELOG.md); current behavior and invariants belong in [`ARCHITECTURE.md`](ARCHITECTURE.md), [`TOOLS.md`](../TOOLS.md), and the focused operational guides.

## Current state

- Public releases: see [GitHub Releases](https://github.com/zoster81/scripthold/releases/latest); **4.0.1** was released through the protected immutable release process on 2026-10-26; post-release semantic fixes remain unreleased.
- Current public capabilities: **36 tools**, **3 guided prompts**, **168 registered text encodings**, and **100 active source-intelligence providers**.
- Completed release changes belong in the [Changelog](../CHANGELOG.md), and the [4.0 migration guide](MIGRATION_4.0.md) covers the unified confirmation tool. Publishing and installing are separate; an active server does not change until it is explicitly updated.

## Planning rules

- At most one release-scoped milestone may be active at a time.
- Define the user-visible outcome, compatibility boundary, security impact, and completion gate before implementation.
- Preserve current filesystem, encoding, mutation, backup, execution, transport, and source-intelligence boundaries unless a milestone explicitly changes them.
- Keep public MCP concepts compact and difficult to misuse.
- Require an exact clean commit and the release procedure in [`PUBLISHING.md`](PUBLISHING.md) for public release authority.
- Do not accumulate implementation diaries or per-phase evidence in this file.

## Active milestone — Source Intelligence structural reliability

**Purpose:** Give an LLM a concise, dependable first map of an unfamiliar project, then let it locate and inspect only the source relevant to its task. Source Intelligence is a set of **read-only evidence and navigation tools**, not an agent, compiler or semantic decision engine. The **LLM** interprets the user request, selects queries, evaluates relevant files and decides what to inspect or provisionally exclude. **Scripthold** returns bounded source facts, locations, supported relations, exact excerpts and honest limitations; it neither chooses the edit site nor judges relevance to the user's task. The agent remains free to use `source_*`, `grep_text_files`, or direct reads; spontaneous tool selection is not a qualification target.

**Released baseline (4.0.1):** `source_symbols` provides `digest`, `outline`, `find`, and fingerprint-verified `show`; `source_query` provides supported structural search, relationships, and context. `outline` defaults to `presentation: "tree"`; callers needing the historical top-level `files` and `symbols` request `presentation: "detailed"`. The separate filesystem `tree` tool describes paths, not source-symbol ownership. See the [tool reference](../TOOLS.md#source_symbols) and [capability matrix](LANGUAGE_CAPABILITIES.md) for the actual contracts. Post-release parser fixes in Git are not proof that an already running connector has been updated.

**Remaining acceptance gates, in dependency order:**

1. **Reuse independent original-project evidence.** Preserve the historical corpus of eight or more original projects per provider where available, without repeating previous passes. For each language/dialect, begin current navigation checks on **two independent projects** (one ordinary, one covering a meaningful variation); expand only for a reproduced problem, an important untested dialect/capability or an affected shared analyzer. Do not mistake historical acquisition for a current test, or require 800 exhaustive project semantic audits. Do not execute third-party code.
2. **Start from a realistic maintenance request.** For each original project, independently select one concrete, source-verifiable behavior to change **before viewing `source_*` outputs**. Use predefined, bounded tool queries to check whether their responses supply evidence for (a) plausible subsystems and distinguishable unrelated matches, (b) relevant behavior and supported direct configuration/consumers/tests, and (c) exact source excerpts. Compare returned facts against independently read source; **do not test spontaneous LLM tool selection or attribute the LLM's decisions to Scripthold**. Independently derive primary edit targets, necessary neighbors and at least one distractor from original source/grep. A plausible candidate is not a confirmed edit location; excluding a file from the *first search* never proves it has no indirect dependency.
3. **Qualify a compact first response and targeted navigation.** Start with scoped `digest` in compact mode, followed by `find`/structural search or kind-filtered `outline` only when the question requires them; use fingerprint-bound `show`/context for the needed declaration. Test each presentation's API contract with focused fixtures, not every presentation on every source file. Correctness, stable IDs, and honest partial/truncated coverage remain mandatory.
4. **Qualify task-directed project navigation.** For the independently selected maintenance scenario, run bounded `digest`/filesystem `tree`, targeted `find`/`source_query search`, supported direct relations and fingerprint-bound `show`/`context` as needed; check that their results provide evidence the LLM can use for edit-area and test discovery, without having Scripthold decide relevance or exclusions. The tool need not infer a full change set, call graph or all affected files; unknown links remain unknown, not safely excluded.
5. **Compare with independent grep/read evidence.** Ask the same navigation question over the same eligible project scope using bounded `source_*` and `grep_text_files` plus targeted reads. Judge both against the independent oracle, **not** by treating every grep hit as a declaration. Record true findings, false positives, omissions, coverage/truncation, relevant structured information, tool calls, output bytes, and latency/memory only when measured. Preserve cases where grep/read is more accurate or efficient.
6. **Fix reproducible defects.** Separate development HEAD from the installed connector and documented unsupported syntax. For confirmed defects, capture a focused failing regression (including relevant original-source evidence), compare minimal implementation alternatives, fix without project-specific exceptions, then verify focused and adjacent behavior. Cover LF/CRLF, BOM/encoding, malformed/oversized inputs, ambiguity, and bounded resource use when applicable.
7. **Stop when a real change can be localized.** Require one independently source-verified maintenance scenario on each of two independent projects: identify a defensible primary edit area, relevant adjacent files/tests, at least one excluded distractor with rationale, and exact source excerpts without fabricated links or oversized first responses. Record a **task-oriented navigation PASS for the checked scope**, not proof of a complete edit plan or whole-project semantic correctness. Escalate when wrong edit targets, important missing capabilities/dialects or shared regressions are demonstrated. Preserve focused contract, encoding, security and promotion checks.
8. **Final standalone MCP qualification (deferred).** Only after project-first structural and handler tests are sufficiently complete, run the separately authorized standalone local MCP server and transport checks. This is deliberately deferred; do not start or restart servers during ordinary source-analyzer development.

**Qualification scope:** An individual PASS applies only to the stated projects, source paths, questions and capabilities. Two-project navigation PASS is the normal current acceptance gate; exhaustive project semantics are optional, not a completion requirement. A successful selected question or `coverageComplete: true` does not prove a complete language grammar, full project hierarchy, or all callers and dependencies. Ruby has 18 complete independently annotated selected files; Groovy and Solidity each now have eight fully annotated selected original files from eight independent projects. These checked scopes do not establish complete language grammars or whole-project navigation; other providers still have representative positive and forbidden checks. None proves that an installed connector contains post-release fixes, and final cross-platform, promotion, and standalone-MCP qualification remain deferred.

Prioritize **shared implementations across the full provider registry**, not an alphabetical language list or a fixed C-then-BASIC queue. Compare the reach of common decoder, scanner, logical-line, symbol-builder, conditional, and handler/index code before choosing where to work. A shared repair requires independent defects and regression checks in its affected consumers; similar syntax alone is not sufficient evidence. Choose the next family by demonstrated severity, reuse potential, available original projects, and verification cost.

**Next focus — expand practical navigation across providers, not C++ compiler emulation.** The original C++ corpus already has eight project-wide structural screenings (1,920 files), focused declaration/definition and fingerprint-safe body tests, and explicit partial coverage for 189 files. Supported cross-file candidates remain structural and ambiguous where ownership or overload identity cannot be proven. Compiler-defined include roots, macro-generated namespaces and unsupported C++ syntax are recorded limitations, **not mandatory parser features**. Preserve those findings and related regressions, but do not repeat whole-project semantic audits. Next, prioritize still-unchecked providers and BASIC/other shared families using two independent original projects per language, three practical navigation questions, and matched grep/read evidence. Escalate C++ or any other family only after a reproducible wrong answer, an important dialect gap or a shared regression.

The C provider's ten original projects already have whole-tree structural screenings (8,265 C/header files); exhaustive compiler-semantic and relationship audits are **not** required for bounded navigation acceptance. The existing C/C++ parser fixes and original-file regression evidence are preserved; do not repeat those baselines without changed inputs or a new defect. Continue with BASIC variants and the remaining providers by proven scanner/parser sharing and defect severity, while retaining the independent per-dialect, per-project acceptance gate. Follow the [project-first qualification checklist](DEVELOPMENT_CHECKLIST.md#source-intelligence-project-first-qualification); do not run third-party project code or the deferred standalone MCP server as a substitute for handler qualification.

Keep comparing the connected runtime, development analyzer, actual Go handlers, and grep/read on the same questions. A fresh defect must be reproduced against current development code before changing a shared parser. Continue tracing common scanner, logical-line, conditional, symbol-builder and source-query/index boundaries across **all 100 providers**, including those not listed above. Languages with similar syntax do not necessarily share implementations; a family fix never replaces the individual provider gate.

**Priority:** P0 — invented or badly misclassified declarations, incorrect owners, wrong source bodies or false relationships that mislead edits; P1 — important missing navigation targets, wrong locations, unsafe source identity, or misleading coverage; P2 — first-pass responses too large to guide an LLM, other resource inefficiency, or lower-impact missing findings; P3 — compiler-exact expansion and uncommon syntax without a demonstrated navigation benefit. Do not trade accuracy or safety for byte savings; escalate only with real evidence.

**Repeatable method:** Follow the [project-first Source Intelligence qualification workflow](DEVELOPMENT_CHECKLIST.md#source-intelligence-project-first-qualification). Independently label original source, compare the connected MCP runtime, development analyzer and an actual local handler test when run, and check grep/read under identical conditions. Record which boundaries remain untested.

**Completion rule:** Stop ordinary provider work when predeclared tool-query sequences derived from a **behavioral change request** succeed on two original projects: source-grounded plausible subsystems/files, supported direct neighbors/tests, distinguishable unrelated matches, and exact source access with honest uncertainty. This qualifies Scripthold's responses, **not** autonomous LLM planning or correct edit decisions. Compare against independent original-source/grep evidence and account for useful facts, false edit leads and response size. No complete compiler semantics or full impact analysis is required. Add projects or parser work for reproduced harmful misdirection, significant dialect/capability gaps or shared regressions; preserve existing security and public contracts.

Cross-platform CI does not certify semantic correctness for every language. Releases follow [Publishing](PUBLISHING.md).
