## Active milestone — Source Intelligence structural reliability

**Purpose:** Give an LLM a concise, dependable first map of an unfamiliar project, then let it locate and inspect only the source relevant to its task. Source Intelligence is a set of **read-only evidence and navigation tools**, not an agent, compiler or semantic decision engine. The **LLM** interprets the user request, selects queries, evaluates relevant files and decides what to inspect or provisionally exclude. **Scripthold** returns bounded source facts, locations, supported relations, exact excerpts and honest limitations; it neither chooses the edit site nor judges relevance to the user's task. The agent remains free to use `source_*`, `grep_text_files`, or direct reads; spontaneous tool selection is not a qualification target.

**Released baseline (4.0.1):** `source_symbols` provides `digest`, `outline`, `find`, and fingerprint-verified `show`; `source_query` provides supported structural search, relationships, and context. `outline` defaults to `presentation: "tree"`; callers needing the historical top-level `files` and `symbols` request `presentation: "detailed"`. The separate filesystem `tree` tool describes paths, not source-symbol ownership. See the [tool reference](../TOOLS.md#source_symbols) and [capability matrix](LANGUAGE_CAPABILITIES.md) for the actual contracts. Post-release parser fixes in Git are not proof that an already running connector has been updated.

### Qualification method and evidence limits

**Project-navigation checks** begin with a realistic maintenance question and complete reads of the selected original sources *before* querying the development handler. Immutable upstream revisions, independent grep/source oracles, plausible neighboring and unrelated files, bounded digest/find/query responses, fingerprint-bound excerpts and truthful coverage are checked together. A PASS certifies only the tested navigation task, not an entire grammar, hidden dependencies, program execution or an LLM's choice to call the tool. The [project-first checklist](DEVELOPMENT_CHECKLIST.md#source-intelligence-project-first-qualification) defines the reusable acceptance criteria. Local original snapshots remain outside tracked files; provider-specific Go tests and Git history retain implementation and verification evidence.

**Retrospective selected-file declaration inventories** are a separate, stricter gate: 22 project cases, 77 fully read original files and 1,913 independently annotated declarations within the stated supported structural syntax. These inventories compare the complete detailed outline against original-source names, native kinds, owners, lines, duplicate/conditional alternatives and negative non-declarations. They are **not** whole-repository or whole-language certification.

### Known limitations and verification boundaries

These caveats describe **current development-tree behavior and unresolved work**, not a list of completed language campaigns. Resolved parser changes belong in the [Unreleased changelog](../CHANGELOG.md#unreleased); the [capability matrix](LANGUAGE_CAPABILITIES.md) and [tool reference](../TOOLS.md#source_symbols) describe supported navigation.

- **ECMAScript-family variable classification is lexical, not runtime type inference.** A binding is indexed as an arrow-function declaration only when its own supported initializer directly declares an arrow; arrows inside object values, calls, conditional alternatives or type annotations do not promote the enclosing variable to a function. In TypeScript, a completely parenthesized direct arrow with a simple `as` or `satisfies` type name also retains its function kind; complex assertion types and compound runtime expressions remain conservatively excluded. A variable initializer split immediately after `=` or a direct `=>` is read as one declaration, preserving the supported function kind and source excerpt. Directly assigned, ungrouped `function`, `async function` and generator expressions with a complete parameter list and body are also indexed as callable `function-expression` bindings; nested, immediately invoked, conditional and compound function-valued expressions remain ordinary values. Parenthesized function-expression wrappers and other continuation syntax can still need direct inspection. Dynamic values, unsupported expressions and runtime type resolution remain outside this subset.
- **TclOO declaration navigation is limited to explicit class bodies.** Classes created with `oo::class create` and their directly declared members are indexed with lexical class ownership; imported `class create` aliases, `oo::define` mutations, inheritance/mixin semantics, indirect command invocation and Tcl execution are not resolved. A recognized subset must not be mistaken for full Tcl/TclOO grammar coverage.
- **JScript.NET returned-object navigation is lexical, not runtime alias resolution.** Direct identifier-key `function` members in nested returned object literals have navigable lexical owners, but assigning an immediately invoked function's result to a variable does not establish that variable as the object's semantic owner. Quoted/computed keys, arrow-valued members, and dynamic aliases remain outside this structural subset.

- **Selected scope is not full grammar coverage.** Even a completely inventoried selected file does not prove unrelated files, every language construct, full ownership semantics, inferred relations, or runtime correctness.
- **GraphQL lexical subset.** In GraphQL, supported top-level named fragments and schema directive definitions are navigable as `section` declarations (`nativeKind: fragment` and `nativeKind: directive`), with direct named directives, supported argument lists, optional `repeatable`, and named locations. Direct line-form enum values, with simple optional annotations, are navigable as `constant` members (`nativeKind: enum-value`) under their owning enums; inline and complex multiline values remain outside this lexical subset. Supported object/input/interface fields now retain directly written same-line type references (including nested lists and non-null modifiers) in fingerprint-verified source excerpts; fields with unproven type syntax mark coverage incomplete rather than extending into siblings. Multiline field argument headers remain navigable; directly attached directive argument lists, including a single intervening LF/CRLF line break, are masked lexically so their named arguments are not mislabeled as type fields. Other complex directive formatting, field argument/default-value/directive semantics, multiline return types, anonymous operations, fragment-spread resolution and query selections remain outside the selected supported-declaration inventory.
- **Coverage and partial files.** A successful `coverageComplete` result means the requested files were processed within the analyzer's declared scope, not that all declarations, call sites, or dependencies were found. Some larger original Lua and D files, MQL4 server scripts, and complex VHDL forms remain partially supported. A shell script with no function declarations can legitimately return no symbols. Keep partial or excluded files distinct from passing maintenance scenarios.
- **Kotlin multiline primary constructor headers have a bounded lexical scope.** A class with an explicit constructor on the following lines (including supported declaration modifiers or annotations) now keeps its full class excerpt and member ownership; accepted continuation spans are limited to eight lines and 4 KiB, and unrelated top-level declarations remain separate. This is not an exhaustive Kotlin grammar. Kotlin package names containing the soft keyword `internal` now retain the full lexical owner, while malformed dotted names report incomplete coverage instead of inventing a shortened package. Other soft-keyword and escaped package names remain outside the independently verified subset and may need direct source inspection.
- **Kotlin value-class navigation is lexical.** Direct and nested supported `value class` definitions are indexed as class symbols (`nativeKind: value-class`) and retain their member ownership; named class excerpts remain fingerprint-verified. Kotlin inline representation, boxing, compiler type checking, and full property accessor semantics are not established by this subset. Original Moshi and Material Files sources verify selected ownership and excerpts, not every value-class form. Directly preceding supported class annotations are retained in the existing class source excerpt, including stacked annotations before value classes, without changing member ownership. File-level annotations and unrelated function/property annotations are kept separate; complex annotation grammar and Kotlin/JVM effects remain outside the qualified subset.
- **Kotlin explicit property getters have bounded source excerpts.** A more-indented `get()` with a single physical expression line, balanced brace body, or selected next-line expression with bounded continuation is included in the property's fingerprint-verified `source_symbols.show` excerpt. The selected multiline subset covers explicit Elvis/member-call chains and balanced `if`/`when` branches; source indentation, paired delimiters, and a 96-line/16-KiB scan bound guard sibling ownership and resource limits. Supported mutable properties also retain a directly indented, single-parameter `set(value) { ... }` with a balanced brace body, alone or following a getter, under the original property identity. Accessors do not become separate symbols. Supported directly preceding `@get:`/`@set:` annotations are retained as source text on class-member and primary-constructor property excerpts without interpreting their JVM effects. Malformed or unsupported setter expressions are reported as incomplete when recognized; annotations embedded within accessor bodies and other complex forms remain outside the independently verified subset and may require direct source inspection. No accessor execution, type checking, full Kotlin grammar or full accessor semantics are implemented.
- **Kotlin enum entries have bounded lexical coverage.** Direct comma-separated entry names, optionally followed by balanced constructor arguments, are indexed as owned `constant` members (`nativeKind: enum-value`). Exact excerpts retain supported argument lists; an optional trailing comma and explicit `;` preserve subsequent methods. Current-development Go-handler checks on independent original Material Files and Okio sources locate 34 selected entries by owner and line, verify representative fingerprint-bound drilldown and structural search, and retain the following Okio method; LF/CRLF checks also cover nested calls and multiline enum headers. Annotated entries, anonymous per-entry class bodies, malformed separators, runtime values and full enum semantics remain unsupported and conservatively partial. Java enum processing is unchanged.
- **Kotlin companion object ownership is source-only.** A directly nested, unnamed `companion object { ... }` with balanced braces now has a structural owner with Kotlin's implicit name `Companion` and `nativeKind: companion-object`, letting `source_symbols` navigate its methods, properties and constants separately from the surrounding class. Since `Companion` is not spelled in that declaration, the name range points to its authored `object` keyword; `show` retains the exact original source. Explicitly named companions and ordinary named objects remain distinct. This does not establish arbitrary object-expression support, compiler binding, runtime initialization or full Kotlin grammar.
- **Kotlin annotated function navigation is lexical.** Supported declaration annotations directly preceding `fun`, optionally with known modifiers, are retained in the method or function's source excerpt; file-level annotations and annotations on classes or properties do not become function prefixes. The bounded classifier does not interpret Kotlin annotations, annotation targets, runtime JVM effects, or malformed/complex forms, which may need direct source inspection.
- **Kotlin wrapped expression navigation is bounded.** When a supported `fun ... =` declaration is immediately followed by a safely delimited, more-indented single physical expression line, fingerprint-verified `source_symbols.show` includes that authored line while preserving a short declaration signature and separating adjacent methods. Multiline chains, unresolved bracket continuations, full Kotlin expression grammar, runtime semantics and type checking are not established; unsupported wrapped forms mark selected-file analysis incomplete.
- **Stylesheet rule navigation is source-only.** For CSS, SCSS and Less, fingerprint-verified `source_symbols.show` includes each supported balanced rule from its complete selector group through the closing brace, preserving authored properties and nested text while excluding adjacent rules. Unclosed braces mark source coverage incomplete. In SCSS, supported `#{...}` expression braces are excluded from rule-boundary detection while authored positions remain stable; malformed interpolation with a declaration terminator or no closing brace marks analysis incomplete. Sass expression evaluation and arbitrary nested interpolation grammar are not established. These indexes do not compute the CSS cascade, resolve imports or Less/SCSS mixins, or infer runtime rendering. Indented Sass is indexed separately: a selector's fingerprint-verified `show` includes its supported direct and nested indented source lines through the last non-comment descendant, excluding neighboring selectors, while compact outline signatures retain only its header. Supported Sass `@function` and legacy `=mixin` definitions likewise retain their directly and transitively indented source lines in fingerprint-verified `show`, while their signatures stay header-only and `+mixin` calls remain invocations, not definitions. Nested indented Sass selectors, including simple escaped pseudo-selector headers such as `\::selection`, comma-separated groups of bare element names such as `body, html`, and whitespace-delimited chains of simple `> tag`, `> #id`, `> .class` and `> *` child-combinator targets, retain their nearest recognized lexical parent in `outline` and `find`, including within Vue Sass style blocks; peers at the same indentation stay separate, and existing selector qualified names remain stable for exact-name queries. Compound selectors, interpolation, malformed chains and other complex combinator expressions are not fully parsed. Direct Sass `$name:` assignments inside a recognized function, legacy mixin or selector likewise retain that nearest indexed lexical parent, even through nested conditionals or media blocks; file-level assignments remain unowned and are not hidden. These relationships describe authored source nesting, not Sass runtime variable scope, `!global` assignments, evaluated functions, resolved mixins, media, imports, complete selector semantics or compiled CSS.
- **Oracle SQL view excerpts are bounded, not database semantics.** `source_symbols.show` for supported SQL views stops at the first unquoted, uncommented `;` or standalone SQL*Plus `/` terminator, whichever occurs first, excluding the following statement and the SQL*Plus execution command. Plain semicolon-terminated views remain unchanged. This lexical boundary does not validate SQL, evaluate queries, interpret SQL*Plus commands, or fully parse procedural SQL bodies.
- **TOML multiline values.** Direct TOML triple-quoted basic and literal multiline key values now retain their complete lexical source range, so `show` can inspect the original full description without reporting headings or assignments embedded in that string as declarations; nested/compound multiline value expressions remain outside this verified subset.
- **JSON and JSONC.** JSON package manifests expose supported object-key paths, including repeated nested export keys, but do not resolve conditional module exports or execute builds. Malformed strict JSON now reports incomplete coverage instead of accepting recoverable keys as proof of a valid document; already identified keys may still be navigable as partial evidence. JSON with comments (JSONC), such as some editor launch configurations, is not strict JSON and requires direct inspection rather than assuming normal JSON navigation.
- **YAML workflows.** YAML workflow navigation now retains the complete source range of directly declared literal/folded block scalars such as `run: |`, including supported indentation indicators, and keeps subsequent sibling keys discoverable. It still reports incomplete coverage for list/step semantics: matching a `run` or `uses` key does not establish a distinct step identity, and related `justfile` or shell commands require direct source inspection.
- **Nix scopes.** Nix indexes supported direct outer `let` bindings while excluding nested attribute-set keys, function-local bindings, and examples inside indented multiline strings from top-level declarations; skipped nested assignments receive an incomplete-coverage diagnostic. Indented strings, supported double-quoted multiline strings, and block-comment contents are masked before let-binding recognition, so embedded assignment-like or `in` text does not invent declarations or terminate the let early; source-derived original flake-parts modules check sibling retention. An outer `let` missing its matching `in` now reports incomplete coverage while leaving discovered bindings navigable, with an original Home Manager let excerpt as the source oracle. Unsupported `inherit` declarations inside `let` expressions, including nested ones, likewise mark coverage incomplete rather than silently hiding inherited names; an original flake-parts inherit block grounds this limit. It still does not index inherited names, root or result attribute sets, interpret string interpolation or implement complete Nix expression parsing.
- **Protocol Buffers.** Protocol Buffers indexes named messages, enums, services, fields and RPCs, plus directly declared `NAME = integer;` enum values with verified ownership. Direct single-line field declarations now preserve their source text through the terminating `;`, including bracketed inline options; unresolved or multiline suffixes are marked partial, not reconstructed. Inline enum members and per-member option lists remain outside the supported index. Directly declared `extend` blocks and their fields are navigable as lexical scopes, but external extended types are not resolved or assigned semantic ownership. Direct Proto2 `group Name = number { ... }` blocks, optionally preceded by a field label, are not indexed: their balanced nested contents are excluded to avoid reporting group-only members under the enclosing message, with explicit incomplete-coverage diagnostics and neighboring fields retained. More complex group headers and group member relationships require direct source inspection. Invalid dotted `message`, `enum`, and `service` declarations are excluded with explicit incomplete-coverage diagnostics; a completed scan is not exhaustive grammar recognition.
- **Terraform/HCL.** Terraform/HCL `resource` and `data` blocks require both quoted labels for safe indexing; missing local labels explicitly mark coverage incomplete and their nested blocks are not promoted to top-level declarations. Module import navigation now accepts only a direct `source` attribute rather than an identically named nested object key, preserving original Kubespray module targets. This does not validate all Terraform expressions, module inputs, or arbitrary HCL syntax.
- **OpenAPI YAML.** OpenAPI YAML route navigation indexes operations with explicit `operationId` and method/path fallbacks for directly declared `paths` entries without one; it does not validate request semantics or resolve JSON/complex YAML structures.
- **Ansible.** Ansible named task source excerpts include directly nested action, guard, notification and registration lines up to the next peer or enclosing YAML block; named play headers remain separate. `import_playbook` references are not followed or treated as runnable tasks, and dynamic role or task behavior is not inferred.
- **Configuration navigation is source-only.** These tools do not evaluate Nix expressions, resolve OpenAPI references, or execute imported playbooks.
- **Large Zig source files may remain partially indexed.** In the original zmx project, `src/main.zig` reports incomplete selected-file coverage. The qualified navigation task uses the narrower configuration, POSIX helper, test-entry, and unrelated-label scope, with an independent direct read of the main entry point; it does not claim complete indexing of the larger file.
- **Some component forms remain conservatively partial.** Vue Options API shorthand methods, shorthand `computed` getters, direct shorthand `watch` callbacks, standard lifecycle hooks and the direct shorthand `data()` initializer are now indexed in the development tree; original Vuetify getters, independent Vue 2 watcher projects and two original Vue 2 components' lifecycle and `data()` methods have bounded development regression checks. String-keyed watch paths, handler objects, watcher arrays, function-valued option entries, dynamic option spreads and computed `get`/`set` object descriptors remain outside this supported scope; original Vue 2 city-list components from two independent projects now confirm `sortgroupcity` getter navigation, including source-linked handler drilldown. Svelte 5 direct object-destructured `$props` bindings (for example `copyCode`) are now indexed in the development source, including aliases, defaults and rest bindings; nested/computed patterns are not fully inferred. Vue `<script setup>` blocks with quoted `generic` type constraints containing `>` now keep their script source boundaries using the shared Svelte quote-aware recognizer; this indexes supported declarations without interpreting TypeScript generic semantics. Astro `<script>` blocks with quoted attribute values containing `>` likewise preserve their script boundaries; this does not interpret Astro component behavior or fully parse HTML attributes. Their `<style>` blocks also keep source boundaries and direct CSS selectors when a quoted opening-tag attribute contains `>`; quoted attribute values are not interpreted as CSS or runtime media-query results. Razor, Blazor, and ASP.NET WebForms now likewise retain direct CSS selectors when a quoted `<style>` attribute contains `>`; a source-derived original Umbraco Razor page verifies selected line positions, while shared synthetic cases cover both quote styles and line endings. The same .NET client hosts preserve script boundaries when an opening-tag attribute contains quoted `>`, with source-derived NopCommerce Razor evidence; this does not imply script execution, CSS media-query evaluation, or complete HTML parsing. The selected Astro/Vue/Svelte tasks do not prove complete component APIs, stylesheet rendering, or browser behavior.
- **Some language constructs are intentionally conservative.** The Ada analyzer preserves direct task/protected specifications as navigable types while excluding unsupported task/protected body declarations and nested members from outer-package navigation through a bounded named lexical `end` or a simple task body's `end;`; it marks this unsupported scope coverage incomplete and resumes after the closing line. Original Universal Ctags Ada task/protected specifications and bodies and an independent Ada GUI protected body exercise these boundaries. Complex nested concurrency scopes, protected/task member relationships, unmatched or unsupported terminators, and generic instantiation semantics still require direct source inspection; separate Sample Programs Ada files are standalone search/shortest-path examples.
- **Tcl and TclOO scopes.** The Tcl analyzer indexes named `proc` commands and supported `namespace eval` scopes. The development tree now also indexes explicit TclOO `oo::class create` classes and their directly declared constructors, methods, and destructors with lexical ownership. The earlier MAL Tcl procedure-navigation checks alone do not certify complete class APIs, imported aliases, dynamic commands, or runtime behavior.
- **Scala XML qualification boundary.** Scala XML's selected 87-declaration audit covers package, type and type-member declarations, not function-local declarations (including local classes/objects and nested functions), macro expansion or Scala compiler semantics.
- **Swift lexical subset.** Swift enum cases and directly nested local function declarations are now indexed, but local declarations inside deeper control-flow or closure scopes, arbitrary function-local variables, conditional compilation semantics and full Swift grammar are not certified; `coverageComplete` must not be interpreted as compiler validation.
- **Other language boundaries.** Dart conditional `import`/`export` directives retain the authored default URI as structural evidence but explicitly mark coverage incomplete and diagnose omitted platform-guarded alternatives; existing dependency fields cannot express guards and must not imply platform resolution. Original independent Hive and Dart Sass sources, LF/CRLF and local MCP `digest` checks qualify the development behavior without executing Dart. Dart `import 'uri' as prefix` (including simple `deferred as`) now carries the locally authored prefix separately from the import URI and its source range; `export`/`part` directives and deferred runtime loading are not treated as imported local prefixes. Two independently read original Dart projects and LF/CRLF/local MCP checks qualify this bounded development behavior, not URI resolution. Groovy `import ... as Alias` and `import static ... as Alias` are indexed as the authored dependency target with the local alias kept separately, not concatenated into a fabricated target. Development-only original-source verification covers independently authored jyreport and Alipsa Matrix files, portable LF/CRLF, and local MCP `digest`; name resolution and Groovy execution are not inferred. Shared brace-language parsing preserves existing non-Groovy import semantics. Ruby `require`/`require_relative` dependency links now require a directly authored simple literal argument: nested `File.join`/`File.expand_path` strings, concatenated targets, interpolation and unproven escaped spellings are not treated as resolved module names. Two independent original Ruby CLI projects verify this bounded development behavior; runtime load paths and computed imports are not resolved. Lua/Luau `require` dependency links now require an immediate literal module argument; nested formatting, concatenated expressions and unrelated `.require`/`:require` methods are excluded rather than promoted as module links. Two independent original Neovim Lua plugins confirm the bounded development behavior, not runtime module resolution. Nested or macro-generated Common Lisp/Clojure/Emacs Lisp forms, advanced D and Lua syntax, complex VHDL types, ambiguous Ruby method bodies, preprocessor directives, generic/type inference, and dynamic dispatch are not universally resolved. Do not manufacture symbols, ownership, callable bodies, or project-wide dependencies where analysis lacks evidence.
- **Structural links are not execution semantics.** The additional COBOL Universal Ctags cases navigate named programs, sections and paragraphs in original printer and embedded-SQL fixtures, while SQLCA data layout and `EXEC SQL INCLUDE SQLCA` must be checked by direct reads; no embedded-SQL dependency resolution or execution is inferred. The separate Rosetta Code COBOL examples cover standalone CSV and graph tasks rather than one application.
- **Assembly sources and includes.** The additional Assembly NASM interpreter navigation locates named labels in selected files; include references and macro definitions require direct source inspection, and the separate x86-64 Sample Programs examples do not form one application.
- **Perl project references.** In the development tree, `require` dependency links now require an immediate authored string literal; strings nested in `File::Spec->catfile(...)` and computed or interpolated targets are not promoted as known modules. Original RegRipper demonstrated the false-link defect; an independently read OpenNMS script checks the adjacent already-correct expression boundary. `use` links and directly quoted `require` targets remain supported, but full Perl module/path evaluation is not. In the additional Perl checks, named subroutines can be located in related MAL modules; calls and namespace dispatch still require original-source inspection. The separate Sample Programs project contains alternative sorting snippets, not an interdependent application.
- **Elixir project references.** In the additional Elixir checks, the Mix entrypoint and MAL cross-module calls also need direct source inspection; the independent Sample Programs project contains standalone sorting examples.
- **Tcl project imports.** The additional Tcl MAL interpreter checks directly read `source` imports alongside its indexed procedures, while the separate Sample Programs Tcl examples are independent search/graph programs, not one application.
- **Cross-file source relationships.** Adjacent Go/TypeScript/R/PHP code, XML/MSBuild imports, GraphQL resolvers, stylesheet consumers, HTML code-behind, and configuration overrides may be inspected directly, but providers do not automatically establish every cross-file semantic relationship.
- **PHP/HTML template linkage.** In the additional CodeIgniter and Joomla PHP/HTML navigation checks, static HTML IDs and named PHP declarations are findable, while view/template selection and JavaScript DOM links require direct source inspection rather than inferred source-query relations.
- **Navigation is not execution.** No original-project execution, compilation, database query, cloud operation, UI rendering, numerical simulation, or runtime correctness is certified by this milestone.
- **Development and installed servers differ.** An installed 4.0.1 connector may predate Git changes. Confirm discrepancies against current development handlers rather than treating an older result as a current-HEAD defect. Fingerprint-bound `show` can correctly refuse oversized source regions with `LIMIT`; narrow the requested declaration or use an authorized targeted source read instead of silently raising resource bounds.
