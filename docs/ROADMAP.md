## First priority: Source Intelligence refactor

**Status: in progress in the development tree; not released.** This remains the **first post-4.1.0 engineering task**, ahead of further parser maintenance and separate durable-task concurrency/Desktop-approval work. Qualified development-only improvements already cover source lookup indexes, context planning (including flat and dependency-aware files), output budgeting, and concise source navigation; their individual results belong in the [Unreleased changelog](../CHANGELOG.md#unreleased), not a second implementation history here. The remaining work is an explicit stop/go review of request freshness, selected project-model lookups, graph-aware context costs, and handler maintainability. Accept another change only with the measured benefit or demonstrated simplification required below; if no candidate qualifies, stop performance-only iteration and proceed to the separate pre-integration qualification without weakening filesystem or output safeguards. The goal is lower latency, allocations, and review complexity in `source_symbols`, `source_query`, and their shared analyzer/index layers **without changing public behavior or widening language support**. No release number is assigned.

**Start with evidence, not a broad rewrite.** Reconfirm the clean development baseline and profile the existing `BenchmarkSourceQueryColdWarmAndLookup`, `BenchmarkSourceQueryMixedLanguageMonorepo`, `BenchmarkSharedProjectResolverScaling`, `BenchmarkSharedProjectIndexPartialRefresh`, `BenchmarkSharedProjectQueryAndContext`, `BenchmarkProjectContextRepeatedImports`, and `BenchmarkSourceSymbolsOperations`. Include small-file warm/cold queries, single-file changes, repeated imports, large generated files, and representative original-source fixtures. Record comparable repeated `ns/op`, `B/op`, allocations, CPU/heap profiles and output fingerprints; isolate filesystem enumeration/fingerprinting from model build and query time. Keep private machine-specific results out of this public roadmap.

**Evaluate these changes in order; implement only proven improvements:**

1. **Request and freshness pipeline:** Profile `filetoolsserver/handler/source_query_index.go` and shared bounded file selection. Look for redundant file metadata probes, traversal work and intermediate slices. Reuse safe request-local facts when their identity and lifetime are proven; **never** replace content fingerprint checks with timestamps, reuse stale files, bypass allowed-root/reparse validation, or weaken race detection.
2. **Targeted project-model lookups:** In `internal/sourceintelligence/project_query.go`, `project_context.go`, and `project_resolver.go`, measure repeated linear scans in symbol/position selectors, source-side reference lookups, owner lookup and same-file resolution. Compare (A) retaining current bounded scans, (B) reusing existing `symbolsByFile`, `symbolsByName`, `symbolsByQualified` and `referencesByTarget` more effectively, and (C) building the smallest useful per-file/per-immutable-generation index. Index only when profiling justifies the extra memory and build time. Bound index growth in symbols/references and retained generations; preserve stable pointers, canonical keys, deterministic tie-breaks and explicit ambiguity.
3. **Context planning and allocation:** Reduce unnecessary per-request copies and temporary maps around `PlanContext` and repeated imports. Prefer bounded plan-local reuse and stable sorted slices. Do not publish mutable caches, share query scratch across requests, or increase retained source bodies.
4. **Handler maintainability:** `source_symbols` and `source_query` now share root validation, bounded file selection, and aggregate-byte preflight without changing public results. Continue consolidating only genuinely identical limit/error mapping and split remaining dispatch functions where this lowers review complexity. Keep `source_query` fingerprint and generation checks separate; preserve public JSON projections, diagnostics, output budgets and operation-specific defaults.
5. **Shared parsers last:** Do not reorganize 100 providers for stylistic uniformity. Refactor a scanner, symbol builder or family analyzer only for a separately demonstrated maintenance/performance problem, with every directly affected provider and negative syntax case requalified.

**Design and challenge gate:** For every proposed slice, compare the minimal local change, a focused index/reuse alternative and leaving the existing code intact. Quantify time/space complexity and bounded memory multiplied by retained project generations. Explicitly reject global/persistent indexes, general parser rewrites, unsafe mutable shared state and duplicate helper layers without compelling benchmark and regression evidence. Check cancellation, concurrency, stale cursors/generations, changed bytes, duplicate identities, pointer/slice aliasing, deterministic ordering, partial/truncated coverage, malformed/oversized inputs, encoding/BOM, Windows paths and cross-platform behavior. Revisit the alternatives if these checks expose a better design.

**Acceptance and stop rule:** Capture a baseline before each edit; use focused TDD plus golden/structural comparisons of `source_symbols` (digest, outline, find, show) and `source_query` (search, relations, context), in detailed and concise modes. Match normalized symbols, IDs, ownership, ranges, relationships, fingerprint/staleness policy, ordering, ambiguity, coverage, truncation, errors, and serialized public responses for unchanged inputs. Run focused model/handler tests, benchmarks with multiple repetitions, race checks for touched shared-state boundaries, and the full regression/static/security and original-source family gates before protected integration. A **performance-only** change must show repeatable improvement (aim for at least 15% median latency or 20% fewer allocated bytes on a representative affected workload) without a reproducible greater-than-10% regression elsewhere; otherwise revert or reject it. A maintainability-only extraction must measurably simplify reviewed code with equivalent results and no material resource regression. Keep each accepted increment narrowly scoped, reviewed and independently reversible; do not restart/deploy the installed server or imply a release.

## Source Intelligence structural reliability — source-level gate complete

**Purpose:** Give an LLM a concise, dependable first map of an unfamiliar project, then let it locate and inspect only the source relevant to its task. Source Intelligence is a set of **read-only evidence and navigation tools**, not an agent, compiler or semantic decision engine. The **LLM** interprets the user request, selects queries, evaluates relevant files and decides what to inspect or provisionally exclude. **Scripthold** returns bounded source facts, locations, supported relations, exact excerpts and honest limitations; it neither chooses the edit site nor judges relevance to the user's task. The agent remains free to use `source_*`, `grep_text_files`, or direct reads; spontaneous tool selection is not a qualification target.

**Published 4.1.0 behavior:** `source_symbols` provides `digest`, `outline`, `find`, and fingerprint-verified `show`; `source_query` provides supported structural search, relationships, and context. `outline` defaults to `presentation: "tree"`; callers needing the historical top-level `files` and `symbols` request `presentation: "detailed"`. The separate filesystem `tree` tool describes paths, not source-symbol ownership. See the [tool reference](../TOOLS.md#source_symbols) and [capability matrix](LANGUAGE_CAPABILITIES.md) for the actual contracts. The 4.1.0 fixes are published but do not change an existing running connector until that installation is explicitly updated.

### Follow-on maintenance — evidence-led structural reliability

**Future defect intake:** Maintain the deduplicated, reproducible backlog derived from original-source `source_symbols.outline` comparisons; reopen parser work only for independently reproduced new current-development defects. Prioritize missing or invented declarations and incorrect ownership, then symbol identity/kind and source ranges. Group cases by actual shared analyzer implementation rather than assuming language-by-language isolation; distinguish supported defects, intentionally unsupported syntax, candidates, and source-oracle corrections. A complete sample audit does not certify a whole language or a defect-free provider.

**Change gate:** For each selected causal cluster, establish a source-first original-project expectation and a genuine failing test on the current development analyzer, implement the minimal compatible fix, and run targeted original-source and handler tests. Requalify affected shared providers plus dependent `source_symbols` and `source_query` operations as regression checks, with broader race, static and full-suite verification as required by the [development checklist](DEVELOPMENT_CHECKLIST.md). Keep interim source provenance, local audit findings and task state in private operator records; only independently reproducible, accepted behavior changes belong in tracked changelog/docs. No release or installed-server update is implied.

### Known limitations and verification boundaries

These caveats describe **4.1.0 source behavior and unresolved limitations**, not a list of completed language campaigns. Released parser changes belong in the [4.1.0 changelog](../CHANGELOG.md#410---2026-11-20); the [capability matrix](LANGUAGE_CAPABILITIES.md) and [tool reference](../TOOLS.md#source_symbols) describe supported navigation.

- **Nim import resolution remains lexical.** A simple `from module import name` records the module, not selected symbols; a composed `from "quoted-root" / module/path import name` also records its one logical lexical source module when the root is a plain quoted path or the symbolic `$nim` prefix, with the source range over the authored expression rather than any inferred filesystem resolution. A direct simple `import module as alias` preserves its module and local alias separately. Simple grouped `import prefix/[one, two]` and spaced `prefix / [one, two]` forms emit one logical source-unit dependency per member, using each authored member token as the navigable source range; the shared prefix is logically joined and cannot be represented by one contiguous range. A simple `import module except excludedName[, excludedName]` records the source module, not excluded symbol names, including when the path is an unescaped double-quoted literal; the module's authored token range remains available. Malformed, nested or aliased grouped expressions, unsupported aliases and complex `except` expressions mark analysis incomplete with a source-ranged warning instead of inventing targets. Excluded-member binding, Nim compilation and full import grammar remain outside the independently verified subset.
- **ECMAScript-family variable classification is lexical, not runtime type inference.** A binding is indexed as an arrow-function declaration only when its own supported initializer directly declares an arrow; arrows inside object values, calls, conditional alternatives or type annotations do not promote the enclosing variable to a function. In TypeScript, a completely parenthesized direct arrow with a simple `as` or `satisfies` type name also retains its function kind; complex assertion types and compound runtime expressions remain conservatively excluded. A variable initializer split immediately after `=` or a direct `=>` is read as one declaration, preserving the supported function kind and source excerpt. Directly assigned, ungrouped `function`, `async function` and generator expressions with a complete parameter list and body are also indexed as callable `function-expression` bindings; nested, immediately invoked, conditional and compound function-valued expressions remain ordinary values. Parenthesized function-expression wrappers and other continuation syntax can still need direct inspection. Dynamic values, unsupported expressions and runtime type resolution remain outside this subset.
- **TclOO declaration navigation is limited to explicit class bodies.** Classes created with `oo::class create` and their directly declared members are indexed with lexical class ownership; imported `class create` aliases, `oo::define` mutations, inheritance/mixin semantics, indirect command invocation and Tcl execution are not resolved. A recognized subset must not be mistaken for full Tcl/TclOO grammar coverage.
- **JScript.NET returned-object navigation is lexical, not runtime alias resolution.** Direct identifier-key `function` members in nested returned object literals have navigable lexical owners, but assigning an immediately invoked function's result to a variable does not establish that variable as the object's semantic owner. Quoted/computed keys, arrow-valued members, and dynamic aliases remain outside this structural subset.

- **Selected scope is not full grammar coverage.** Even a completely inventoried selected file does not prove unrelated files, every language construct, full ownership semantics, inferred relations, or runtime correctness.
- **GraphQL lexical subset.** In GraphQL, supported top-level named fragments and schema directive definitions are navigable as `section` declarations (`nativeKind: fragment` and `nativeKind: directive`), with direct named directives, supported argument lists, optional `repeatable`, and named locations. Direct line-form enum values, with simple optional annotations, are navigable as `constant` members (`nativeKind: enum-value`) under their owning enums. Simple complete single-physical-line enum bodies with plain member names separated by whitespace or GraphQL-ignored commas now also retain exact named member ranges; they are bounded to 4 KiB and 128 names, with malformed or unsupported punctuation/directives diagnosed as incomplete instead of inventing members. More complex inline directives and mixed-line or complex multiline enum values remain outside this lexical subset. Supported object/input/interface fields now retain directly written same-line type references (including nested lists and non-null modifiers) in fingerprint-verified source excerpts; fields with unproven type syntax mark coverage incomplete rather than extending into siblings. Multiline field argument headers remain navigable; directly attached directive argument lists, including a single intervening LF/CRLF line break, are masked lexically so their named arguments are not mislabeled as type fields. Simple top-level named operations with directly attached, lexically paired `{ ... }` selection blocks now preserve the entire authored declaration as a bounded source excerpt (maximum 256-byte header gap, 16 KiB declaration and 128 lines), including nested braces; a bounded direct variable-definition subset also preserves the full selection source excerpt for comma-separated `$name: Type` parameters (up to 16), including one-level list/non-null type markers and simple numeric/enum defaults within a 512-byte lexical scan and the same 256-byte operation-header gap. A further bounded direct-annotation subset now retains the full source excerpt for up to four argument-free named operation directives (`@name`) and one direct argument-free annotation per supported variable, including multiline variable declarations. Nested object/list/string defaults, directive calls with arguments, unsupported syntax, malformed, ambiguous or oversized selections remain header-only; no GraphQL directive or variable values or operation semantics are interpreted. This does **not** index query-selection fields or execute GraphQL. Other complex directive formatting, field argument/default-value/directive semantics, multiline return types, anonymous operations, fragment-spread resolution and query selections remain outside the selected supported-declaration inventory.
- **Coverage and partial files.** A successful `coverageComplete` result means the requested files were processed within the analyzer's declared scope, not that all declarations, call sites, or dependencies were found. Some larger original Lua and D files, MQL4 server scripts, and complex VHDL forms remain partially supported. A shell script with no function declarations can legitimately return no symbols. Keep partial or excluded files distinct from passing maintenance scenarios.
- **Kotlin multiline primary constructor headers have a bounded lexical scope.** A class with an explicit constructor on the following lines (including supported declaration modifiers or annotations) now keeps its full class excerpt and member ownership; accepted continuation spans are limited to eight lines and 4 KiB, and unrelated top-level declarations remain separate. This is not an exhaustive Kotlin grammar. Kotlin package names containing the soft keyword `internal` now retain the full lexical owner, while malformed dotted names report incomplete coverage instead of inventing a shortened package. Other soft-keyword and escaped package names remain outside the independently verified subset and may need direct source inspection.
- **Kotlin value-class navigation is lexical.** Direct and nested supported `value class` definitions are indexed as class symbols (`nativeKind: value-class`) and retain their member ownership; named class excerpts remain fingerprint-verified. Kotlin inline representation, boxing, compiler type checking, and full property accessor semantics are not established by this subset. Original Moshi and Material Files sources verify selected ownership and excerpts, not every value-class form. Directly preceding supported class annotations are retained in the existing class source excerpt, including stacked annotations before value classes, without changing member ownership. File-level annotations and unrelated function/property annotations are kept separate; complex annotation grammar and Kotlin/JVM effects remain outside the qualified subset.
- **Kotlin explicit property getters have bounded source excerpts.** A more-indented `get()` with a single physical expression line, balanced brace body, or selected next-line expression with bounded continuation is included in the property's fingerprint-verified `source_symbols.show` excerpt. The selected multiline subset covers explicit Elvis/member-call chains and balanced `if`/`when` branches; source indentation, paired delimiters, and a 96-line/16-KiB scan bound guard sibling ownership and resource limits. Supported mutable properties also retain a directly indented, single-parameter `set(value) { ... }` with a balanced brace body, alone or following a getter, under the original property identity. Accessors do not become separate symbols. Supported directly preceding `@get:`/`@set:` annotations are retained as source text on class-member and primary-constructor property excerpts without interpreting their JVM effects. Malformed or unsupported setter expressions are reported as incomplete when recognized; annotations embedded within accessor bodies and other complex forms remain outside the independently verified subset and may require direct source inspection. No accessor execution, type checking, full Kotlin grammar or full accessor semantics are implemented.
- **Kotlin enum entries have bounded lexical coverage.** Direct comma-separated entry names, optionally followed by balanced constructor arguments, are indexed as owned `constant` members (`nativeKind: enum-value`). Exact excerpts retain supported argument lists; an optional trailing comma and explicit `;` preserve subsequent methods. Current-development Go-handler checks on independent original Material Files and Okio sources locate 34 selected entries by owner and line, verify representative fingerprint-bound drilldown and structural search, and retain the following Okio method; LF/CRLF checks also cover nested calls and multiline enum headers. Annotated entries, anonymous per-entry class bodies, malformed separators, runtime values and full enum semantics remain unsupported and conservatively partial. Java enum processing is unchanged.
- **Kotlin companion object ownership is source-only.** A directly nested, unnamed `companion object { ... }` with balanced braces now has a structural owner with Kotlin's implicit name `Companion` and `nativeKind: companion-object`, letting `source_symbols` navigate its methods, properties and constants separately from the surrounding class. Since `Companion` is not spelled in that declaration, the name range points to its authored `object` keyword; `show` retains the exact original source. Explicitly named companions and ordinary named objects remain distinct. This does not establish arbitrary object-expression support, compiler binding, runtime initialization or full Kotlin grammar.
- **Kotlin annotated function navigation is lexical.** Supported declaration annotations directly preceding `fun`, optionally with known modifiers, are retained in the method or function's source excerpt; file-level annotations and annotations on classes or properties do not become function prefixes. The bounded classifier does not interpret Kotlin annotations, annotation targets, runtime JVM effects, or malformed/complex forms, which may need direct source inspection.
- **Kotlin wrapped expression navigation is bounded.** When a supported `fun ... =` declaration is immediately followed by a safely delimited, more-indented single physical expression line, fingerprint-verified `source_symbols.show` includes that authored line while preserving a short declaration signature and separating adjacent methods. Multiline chains, unresolved bracket continuations, full Kotlin expression grammar, runtime semantics and type checking are not established; unsupported wrapped forms mark selected-file analysis incomplete.
- **SystemVerilog top-level programs are source-only.** Directly authored `program Name(...); ... endprogram` blocks, including a bounded `#(...)` parameter header and port list, are indexed as standalone `module`/`nativeKind: program` symbols with exact source, header/body ranges and fingerprint-verified selected excerpts. The scanner skips nested module/interface/package/checker/class/task/function scopes, limits 128 candidates/file, 4-KiB headers and 64-KiB complete blocks; unsupported, malformed, macro-affected, duplicate, unclosed and oversized forms report incomplete analysis. Two independently authored complete original SystemVerilogCourse and All-of-SystemVerilog files, LF/CRLF negative controls, and original MCP `outline`/`show`/`digest` qualify the conservative lexical subset. Scheduling, execution, elaboration and complete SystemVerilog program grammar remain unverified.

## Post-4.1 candidates — durable task concurrency and Desktop approval

These operator-requested changes are **candidates for a future release after 4.1.0**; they are not part of the published 4.1.0 release. Do not treat them as supported by the currently installed server or silently change its launch configuration.

1. **Durable task concurrency across restarts — implemented in the unreleased development tree; isolated process integration qualified.** Published 4.1.0 rejects `MCP_TASK_MAX_CONCURRENCY` changes for an existing task store because its descriptor contains all limits. The development change treats concurrency as a validated **per-process worker scheduling limit**, preserving the original descriptor and all six other durable policy limits. Tests cover 4→8→12→4 across frontend, worker initialization and executor store opens; retained task identity, idempotency and descriptor salt; malformed stored concurrency; and rejection of other limit changes. An additional isolated integration test launches separate frontend, supervisor, worker and executor processes against a temporary private store. Two executor processes remain active while workers reopen with concurrency 8→12→1→4, including an intentionally killed worker and a new worker whose limit is below the existing active count. Both tasks complete once, and the descriptor remains unchanged. No descriptor migration, deletion or automatic live-worker reconfiguration is required. **Still unverified for release:** coordinated upgrades of the installed executable, automatic supervisor respawn after a worker crash, and native foreign-platform process behavior. **This setting bounds durable task concurrency; it does not create additional LLM agents or increase HTTP request capacity.**
2. **Operator-mediated Desktop authorization requested by an LLM.** Consider a separately discoverable `AskUser` request operation that lets an LLM ask the human operator to approve or reject a *specific prepared action*, displaying a Desktop prompt when the approved client/host supports one. For example, if a prepared file edit needs local operator consent, the LLM can request approval with the **existing `previewId`**, operation identity, and a human-readable summary; the operator chooses Approve or Deny, and a permitted caller may then retry the same unchanged prepared operation. Approval must be authenticated to the operator, one-shot, short-lived, bound to the exact prepared bytes, authorized root, requesting session, and operation; denial, timeout, stale previews, and mismatches must fail closed. A human approval may satisfy **Scripthold-controlled** authorization checks; it cannot override a hard restriction enforced by the OpenAI platform or another host that prevents the call altogether. Before committing to a Desktop popup or MCP elicitation integration, verify actual client interoperability and whether recoverable authorization failures can be surfaced to the LLM. No ambient, blanket permission escalation or automatic fallback mutation is allowed.

The concurrency change has an isolated multi-process regression test, but actual installation upgrades, automatic supervisor restart and platform-specific deployment behavior remain separate release gates. The Desktop approval candidate still requires host interoperability evidence, security architecture review, negative tests, and an explicitly scheduled implementation milestone.
